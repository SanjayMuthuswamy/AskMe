## ❓ Common Interview Questions & Answers

---

### 1️⃣ "What is this project about?"

**AskMe** is an intelligent document Q&A system. Users upload a document (PDF or TXT), and the system builds a searchable knowledge base from it. Users can then ask questions in natural language and get accurate, context-aware answers generated by a local LLM.

**Key point:** It's a full-stack RAG (Retrieval-Augmented Generation) application with an agentic architecture — meaning the AI decides *how* to search and answer, not just *what* to answer.

---

### 2️⃣ "What is RAG and why did you use it?"

**RAG = Retrieval-Augmented Generation**

| Without RAG | With RAG |
|-------------|----------|
| LLM answers from training data only | LLM answers from YOUR uploaded documents |
| Can hallucinate facts | Grounded in actual document content |
| Generic, outdated answers | Specific, accurate answers |

**How it works in AskMe:**
1. Document is chunked into ~1500-char pieces
2. Each chunk is embedded into a vector (using `nomic-embed-text`)
3. Vectors are stored in FAISS for fast similarity search
4. When a question is asked, the most relevant chunks are retrieved
5. These chunks are passed as context to Llama 3 to generate the answer

**Why?** LLMs have knowledge cutoffs and can't read your private documents. RAG bridges that gap.

---

### 3️⃣ "What is a ReAct Agent and why did you use one?"

**ReAct = Reasoning + Acting**

Instead of a fixed pipeline (always do A → B → C), a ReAct agent **thinks** and **decides** which tool to use:

```
Question: "What is the chunk size?"
   │
   ▼
Thought: "This has a specific keyword, I should use BM25"
Action: search_bm25("chunk size")
Observation: Found 3 relevant chunks
Thought: "Let me rerank for accuracy"
Action: rerank_results("chunk size")
Observation: Top 3 reranked results
Thought: "I have enough context"
Final Answer: "The chunk size is 1500 characters..."
```

**My agent has 3 tools:**

| Tool | When Used | Technology |
|------|-----------|------------|
| `search_faiss` | Meaning-based queries ("explain how X works") | FAISS vector similarity |
| `search_bm25` | Keyword queries ("what is the value of Y") | BM25Okapi scoring |
| `rerank_results` | After any search, to improve precision | CrossEncoder ms-marco-MiniLM |

**Why agent over a fixed pipeline?** Different questions need different search strategies. The agent adapts automatically.

---

### 4️⃣ "Explain the hybrid retrieval approach"

I use **two complementary search methods:**

| | FAISS (Semantic) | BM25 (Keyword) |
|---|---|---|
| **How** | Cosine similarity on vector embeddings | Token frequency-based scoring |
| **Good at** | Understanding meaning and context | Finding exact terms and names |
| **Example** | "How does the system process files?" | "What is Sanjay's name?" |
| **Weakness** | May miss exact keywords | Doesn't understand meaning |

**Together, they cover both semantic understanding and exact-match precision.**

The agent decides which to use based on the query type.

---

### 5️⃣ "What is cross-encoder reranking and why is it needed?"

**Problem:** FAISS/BM25 retrieve ~10 candidates, but not all are equally relevant.

**Solution:** Cross-encoder reranking.

```
10 retrieved chunks
       │
       ▼
┌──────────────────────────┐
│  CrossEncoder Model      │
│  ms-marco-MiniLM-L-6-v2 │
│                          │
│  Scores each (query,     │
│  chunk) pair for         │
│  relevance               │
└──────────┬───────────────┘
           │
           ▼
   Top 3 most relevant chunks
```

| Stage | Model | Speed | Accuracy |
|-------|-------|-------|----------|
| Retrieval (FAISS/BM25) | Bi-encoder | ⚡ Fast | Good |
| Reranking | Cross-encoder | 🐢 Slower | Excellent |

**Why?** Bi-encoders (FAISS) encode query and document separately — fast but approximate. Cross-encoders process query+document together — slower but much more precise. This two-stage approach gives us **speed AND accuracy**.

### 6️⃣ "Why Ollama instead of OpenAI API?"

| | Ollama (Local) | OpenAI API |
|---|---|---|
| **Privacy** | ✅ Data never leaves your machine | ❌ Data sent to cloud |
| **Cost** | ✅ Free | ❌ Pay per token |
| **Internet** | ✅ Works offline | ❌ Requires internet |
| **Latency** | ⚡ No network round-trip | 🐢 API latency |
| **Control** | ✅ Full model control | ❌ Depends on provider |

**Trade-off:** Local models (Llama 3 8B) are less powerful than GPT-4, but for document Q&A with good retrieval, they perform excellently.

### 7️⃣ "Why upload a document each time? How would you make it persist across multiple documents?"

**Why single-session upload currently?**
- **Focused Scope & Privacy**: In an interactive session-based RAG tool, rebuilding the index per document session guarantees strict document isolation (no cross-document context leaks) and keeps memory consumption minimal on a local machine.

**How to answer in an interview when asked how to support multi-document persistent queries:**
1. **Persistent Vector Database**: Replace in-memory FAISS with a persistent DB like **ChromaDB**, **Qdrant**, or **pgvector**.
2. **Metadata Filtering & Document IDs**: Store `doc_id` and `file_name` in the payload metadata of each chunk.
3. **Multi-Document RAG Querying**: Allow users to query across all previously uploaded documents simultaneously or filter queries by specific `doc_id` tags.

---

### 8️⃣ "Why did you use FAISS as your vector store?"

**Why FAISS (Facebook AI Similarity Search)?**
1. **Ultra-Fast In-Memory Similarity Search**: FAISS is written in C++ with Python bindings, optimized for high-performance vector indexing and sub-millisecond similarity search.
2. **Zero Setup Overhead**: Requires no standalone database service, daemon, or server container running in the background.
3. **Low Memory & Resource Footprint**: Perfect for local-first desktop applications running alongside Ollama on standard consumer hardware.
4. **Seamless Integration**: Native `langchain_community` support (`FAISS.from_documents()`).

**Comparison with alternatives:**
- **VS ChromaDB / Qdrant**: Chroma/Qdrant offer built-in disk persistence out-of-the-box, but FAISS provides faster raw in-memory retrieval without database file management overhead for single-session document analysis.
- **VS Pinecone / Weaviate**: Cloud vector databases introduce API latency, internet dependency, and token/storage costs, defeating our 100% local privacy design.

---

### 9️⃣ "How did you optimize for low latency and zero/minimal token cost?"

**1. Zero API Token Cost ($0)**
- **Local LLM & Embedding Inference**: Used `Ollama` (`llama3.2`) and local `nomic-embed-text` embeddings. Everything executes on device with $0 API bill and no rate limits.

**2. Two-Stage RAG (Bi-Encoder Retrieval + Cross-Encoder Reranking)**
- **Bi-Encoder FAISS/BM25**: Fast retrieval fetches ~10 candidate chunks in milliseconds.
- **Cross-Encoder Reranker (`ms-marco-MiniLM-L-6-v2`)**: Filters the 10 candidates down to **Top 3 most relevant chunks**.
- **Context Window Optimization**: By passing only the top 3 reranked chunks (~1000 tokens) to the LLM instead of all 10 chunks (~4000+ tokens), we **reduce prompt processing time by over 60%** and keep memory consumption minimal.

**3. Model & Chunking Optimizations**
- **Optimal Chunk Size**: Chunks of 1500 chars with 100 overlap balance context quality without ballooning token counts.
- **Local Pre-loading**: Models (`ms-marco-MiniLM`) are pre-loaded in memory during document upload to avoid warm-up delays when users type questions.

### 8️⃣ "What challenges did you face?"

| Challenge | Solution |
|-----------|----------|
| **LLM hallucination** | RAG grounds answers in actual document content |
| **Slow model loading** | Pre-load cross-encoder during upload, not at query time |
| **Mixed query types** | Hybrid FAISS + BM25 with agent-based tool selection |
| **Retrieval noise** | Cross-encoder reranking filters low-relevance chunks |
| **Agent parsing errors** | `handle_parsing_errors=True` + `max_iterations=5` cap |
| **Large documents** | Chunking with overlap prevents context fragmentation |

### 🔟 "How does the frontend connect to the backend?"

**Two API calls — that's it:**

```typescript
// services/api.ts

// 1. Upload a document
POST http://127.0.0.1:8000/api/upload
Body: FormData { file: <uploaded_file> }
Response: { message, chunks, time_taken }

// 2. Ask a question  
GET http://127.0.0.1:8000/api/ask?query=<question>
Response: { query, answer, time_taken }
```

**State flow:**
1. User uploads file → `UploadPage.tsx` calls `uploadDocument()` → backend builds indexes
2. Upload succeeds → `DocumentContext` stores document name + sets `knowledgeBaseGenerated = true`
3. User navigates to Ask page → `AskPage.tsx` checks context, redirects to upload if no doc
4. User types question → `askQuestion()` calls backend → agent processes → answer displayed in chat
